# Chromium и автозапуск SDO

В `mos12_ansible_w10k22-main/files/home_student/.config/autostart/chromium.desktop`
запускается `chromium-browser ... http://sdo.1580.ru/`. Это XDG-автозапуск при
входе student в графическую сессию, не при одном только включении компьютера.
`files/rc.local` восстанавливает этот файл и намеренно удаляет его на панелях
p1580. Для test отдельного автозапуска в исходниках нет.

`--incognito` добавляется в `.bashrc`. Графическая сессия не обязана читать
этот файл: для гарантированного инкогнито сисадмину следует добавить
`--incognito` непосредственно в существующую строку Exec, сохранив остальные
аргументы и системные настройки прокси. Изменять весь autostart от имени
агента не следует: его источником остаётся Ansible сисадмина.

Наше расширение явно разрешает домен 1580.ru, не применяет к нему скрытие
элементов и не закрывает вкладку SDO. Агент не удаляет chromium.desktop и
не заменяет policies.json с домашней страницей.

Исправлен дефект de_chromium_lock: после смены hostname и завершения Chromium
оставшийся Unix socket inode ошибочно считался живым браузером. Теперь
проверяется соединение с сокетом; только ENOENT/ECONNREFUSED вместе с отсутствием
старого PID разрешают удалить неизменившийся SingletonLock. Живые процессы,
слушающий сокет, неоднозначные ошибки и профили текущего hostname сохраняются.
Сервис работает перед display-manager; текущие окна не перезапускаются.

Проверка 2026-11-28: Chromium под Linux test с --incognito открыл
http://sdo.1580.ru/ → https://sdo.1580.ru/, HTTP 200, заголовок
«В начало | ЦДО школы № 1580». Три теста воспроизводят мёртвый socket inode,
живой слушающий сокет и живой PID. Проверенный 2k-418-9 в момент диагностики
не отвечал; причина конкретного случая требует проверки проблемного устройства
после его подключения. Нельзя считать наличие stale lock доказанным на нём.
